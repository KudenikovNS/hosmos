# Hosmos — правила для агентов

Общие правила для любой работы агента в этом репозитории (Codex, Claude Code и др.). Обзор проекта и ссылки на документацию — в `README.md`; здесь только то, что легко нарушить, не зная проекта.

## База данных

- **DB-тесты делают `TRUNCATE ... CASCADE`** (`src/server/db/__tests__/harness.ts`). Никогда не запускайте `npm test` с `DATABASE_URL`, указывающим на docker-compose или любую другую базу с данными, независимо от порта и имени. Для тестов — только одноразовая база:

  ```sh
  scripts/review-db.sh run -- npm test   # новый контейнер postgres:13 на запуск, удаляется в любом случае
  ```

  Каждый запуск получает свой контейнер с уникальным именем, поэтому параллельные запуски не мешают друг другу. Без `DATABASE_URL` интеграционные сьюты пропускаются (`describe.skip`): зелёный итог при этом не означает, что работа с БД проверена.

- **Не запускайте приложение для проверок в рабочем дереве** (`npm run dev`): `next dev` читает `.env*` и возьмёт настоящие SMTP, ключи Revolut и `DOCUMENTS_DIR`. Для проверок в браузере есть `scripts/review-db.sh run -- scripts/review-app.sh 3147`: временная копия без `.env`, тестовое окружение, одноразовые база и хранилище.

- **Не генерируйте миграции через `drizzle-kit generate`** (npm-скрипт `db:generate` удалён намеренно). Миграции в `drizzle/` пишутся вручную, журнал `drizzle/meta/_journal.json` правится руками (`drizzle/README.md`). Применённые миграции не редактируются, изменения — только новой миграцией.
- **Прод — PostgreSQL 13.23** (общий cPanel-кластер, обновить нельзя). Конструкции PG 14+ в миграциях запрещены.
- Частичные индексы объявлены и в `.sql`, и в `schema.ts`; правьте их парами, источник истины — `.sql`.
- Тесты делят одну базу: `fileParallelism: false` в `vitest.config.ts` не менять, DB-команды параллельно не запускать.
- Продовый путь миграций — `node scripts/migrate.mjs` (его вызывает деплой), без сидов. `npm run db:seed` — только для локальных фикстур.

## Окружение и секреты

- Не читайте и не выводите `.env`, ключи, строки подключения. Контракт переменных — `.env.example`.
- `next build` сам подхватывает `.env*`: для изолированной сборки нужна копия без секретных env-файлов или явный whitelist окружения.
- `NEXT_PUBLIC_*` вшиваются в клиент **при сборке**. Значение, заданное только в runtime (cPanel, `docker run -e`), до браузера не доходит.
- Внешние интеграции (Revolut, SMTP, регистрация вебхуков, крон биллинга) не вызывать по-настоящему: в тестах они мокаются.

## Доставка

- Цель — neoserv.si (cPanel/Passenger), артефакт `.next/standalone`, деплой — `.github/workflows/deploy.yml` на push в `main`. Dockerfile — отдельный путь исполнения, не прод.
- `DOCUMENTS_DIR` должен быть вне каталога, который заменяет rsync.

## Проверки перед мерджем

```sh
./node_modules/.bin/tsc --noEmit --incremental false
npm run lint
npm run format:check
npm test                                  # с одноразовой БД, см. выше
npm run build && npm run check:standalone
```

## Ревью и известные дефекты

- Скиллы ревью лежат в `.ai/skills/` (подключены в `.claude/skills/` и `.agents/skills/`), описание — в `.ai/README.md`. Отчёты — `docs/reviews/`.
- `src/server/__tests__/review/known-defects.integration.test.ts` фиксирует подтверждённые, но ещё не исправленные дефекты (`knownDefect`). Если после вашего изменения такой тест упал с сообщением «больше не воспроизводится», значит, дефект исправлен: замените `knownDefect` на `regressionTest` с теми же аргументами. На обычный `it` заменять нельзя: он не выполняет проверку, которую возвращает `arrange`, и тест станет пустым. Статус в `findings.json` обновит следующий `recheck`; текущие открытые находки показывает `node scripts/review-findings.mjs`.
- Отчёты ревью — снимок на момент запуска: номера строк в них устаревают. Перед исправлением сверяйтесь с текущим кодом.
